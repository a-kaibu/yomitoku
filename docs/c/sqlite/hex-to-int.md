## ひとことで

`sqlite3HexToInt` は、16 進数の 1 文字を 0〜15 の数に変換する関数です。
`'7'` なら 7、`'b'` や `'B'` なら 11 を返します。
数字か英字かを `if` で場合分けせず、**文字コードのビットの性質を使った 1 行の計算** で変換しています。

## コード

::: code-group

```c:line-numbers=1859 [日本語訳]
/*
** 16 進数の 1 バイトを整数に変換する。
** この関数は h が本当に正しい 16 進数の文字
** （0..9a..fA..F）のときだけ正しく動く。
*/
u8 sqlite3HexToInt(int h){
  assert( (h>='0' && h<='9') ||  (h>='a' && h<='f') ||  (h>='A' && h<='F') );
#ifdef SQLITE_ASCII
  h += 9*(1&(h>>6));
#endif
#ifdef SQLITE_EBCDIC
  h += 9*(1&~(h>>4));
#endif
  return (u8)(h & 0xf);
}
```

```c:line-numbers=1859 [原文]

** Translate a single byte of Hex into an integer.
** This routine only works if h really is a valid hexadecimal
** character:  0..9a..fA..F

#endif
#ifdef SQLITE_EBCDIC
  h += 9*(1&~(h>>4));
#endif

```

## 前提知識

- **文字コード（ASCII）**: コンピュータは文字を数で表します。ASCII では `'0'`〜`'9'` が 48〜57（16 進数で `0x30`〜`0x39`）、`'A'`〜`'F'` が 65〜70（`0x41`〜`0x46`）、`'a'`〜`'f'` が 97〜102（`0x61`〜`0x66`）です。
- **EBCDIC**: IBM のメインフレームなどで使われる、ASCII とは別の文字コードです。SQLite はこちらにも対応しています。
- **`int h`**: 文字を `int`（整数）として受け取っています。C では文字は小さな整数として扱えます。
- **`>>`（右シフト）と `&`（AND）**: `h >> 6` は `h` を 6 ビット右にずらします。`1 & (...)` は一番下のビットだけを取り出すので、結果は 0 か 1 です。
- **`h & 0xf`**: 下位 4 ビットだけを取り出します。0〜15 の値になります。
- **`#ifdef`**: そのマクロが定義されているときだけ、`#endif` までのコードを有効にします。ASCII 用と EBCDIC 用で式を切り替えています。
- **`assert`**: 前提条件をデバッグ時に確かめるマクロです。ここでは「本当に 16 進数の文字が来る」ことを前提にしています。

## 何をしているか

### 1. 前提を確かめる

```c:line-numbers=1865
  assert( (h>='0' && h<='9') ||  (h>='a' && h<='f') ||  (h>='A' && h<='F') );
```

`assert` で、`h` が 16 進数の文字であることを確かめます。この関数はそれ以外の文字には正しく動かないので、呼び出し側があらかじめ検査しておく約束です。

### 2. 英字なら 9 を足す

```c:line-numbers=1867
  h += 9*(1&(h>>6));
```

`h >> 6` の一番下のビットは、文字コードのビット 6 です。ASCII では、数字（`0x30` 台）はビット 6 が 0、英字（`0x40` 台と `0x60` 台）はビット 6 が 1 です。
つまり `1&(h>>6)` は **数字なら 0、英字なら 1** になります。それに 9 を掛けて足すので、英字のときだけ 9 が足されます。

### 3. 下位 4 ビットを取り出す

```c:line-numbers=1872
  return (u8)(h & 0xf);
```

具体的な値で追ってみます。

- `'7'` は `0x37`。数字なので何も足さず、`0x37 & 0xf = 7` です。
- `'B'` は `0x42`。英字なので 9 を足して `0x4B`、`0x4B & 0xf = 0xB = 11` です。
- `'b'` は `0x62`。9 を足して `0x6B`、下位 4 ビットはやはり `0xB = 11` です。

英字の `'A'` は下位 4 ビットが 1、`'F'` は 6 なので、9 を足すとちょうど 10〜15 になる、という仕掛けです。大文字と小文字は上位のビットだけが違い、下位 4 ビットは同じなので、どちらも同じ結果になります。

### 4. EBCDIC の場合

```c:line-numbers=1869
#ifdef SQLITE_EBCDIC
  h += 9*(1&~(h>>4));
#endif
```

EBCDIC では、数字が `0xF0`〜`0xF9`、英字が `0xC1`〜`0xC6` や `0x81`〜`0x86` に並びます。数字はビット 4 が 1、英字はビット 4 が 0 なので、`~`（ビット反転）を使ってビット 4 が 0 のときに 9 を足しています。考え方は ASCII と同じです。

## ここがすごい

- **分岐がない**: 素直に書くと `if (h <= '9') return h - '0'; else if (h <= 'F') ...` のように比較と分岐が並びます。この関数はシフト・AND・掛け算・足し算だけなので、CPU の分岐予測（次にどちらへ進むかの予想）が外れて遅くなる心配がありません。16 進数の文字列を大量に読む `x'...'` 形式の BLOB の解析などで効いてきます。
- **文字コードの「並び方」を読み解いている**: ASCII で英字の下位 4 ビットが 1 から始まることと、ビット 6 で数字と英字を区別できることの 2 つを組み合わせています。表を持たずに済み、メモリも使いません。
- **大文字と小文字を同時に扱える**: `'A'` と `'a'` はビット 5 だけが違います。下位 4 ビットしか見ないので、大文字小文字の区別をする処理がまったく要りません。
- **前提を呼び出し側に任せる**: 不正な文字の検査をこの関数でしないことで、1 文字あたりの処理を最小にしています。そのかわり `assert` で前提をはっきり書き、`sqlite3Isxdigit` などで先に調べるのは呼び出し側の責任としています。

## まとめ

- ASCII では、数字と英字はビット 6 で区別でき、英字の下位 4 ビットは 1 から始まる。
- `1&(h>>6)` のように特定のビットを 0/1 として取り出し、掛け算に使うと分岐を消せる。
- 下位 4 ビットだけを見れば、大文字小文字の違いを気にせず済む。
- 入力の検査を省いた速い関数は、前提を `assert` で明示しておく。
