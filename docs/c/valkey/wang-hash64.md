## ひとことで

`wangHash64` は、64 ビットの整数を受け取って、**ビットをよくかき混ぜた** 64 ビットの整数を返すハッシュ関数です。Thomas Wang が考案した整数ハッシュとして知られています（コメントでは Tomas と表記されています）。
`1` と `2` のような近い値を入れても、出力はまったく似ていない値になります。
ハッシュテーブルなどで、連続した整数（ポインタやID）を均等にばらけさせるのに役立ちます。

## コード

```c:line-numbers=1720
/* Tomas Wang's 64 bit integer hash */
uint64_t wangHash64(uint64_t hash) {
    hash = (~hash) + (hash << 21); /* hash = (hash << 21) - hash - 1; */
    hash = hash ^ (hash >> 24);
    hash = (hash + (hash << 3)) + (hash << 8); /* hash * 265 */
    hash = hash ^ (hash >> 14);
    hash = (hash + (hash << 2)) + (hash << 4); /* hash * 21 */
    hash = hash ^ (hash >> 28);
    hash = hash + (hash << 31);
    return hash;
}
```

## 前提知識

- **`uint64_t`**: 符号なし 64 ビット整数です。計算が 64 ビットを超えたら、上の桁は捨てられます（2^64 で割った余りになる）。符号なし整数ではこれは正式に決められた動作で、ハッシュ関数ではわざとこの性質を使います。
- **左シフト `<<`**: `x << 3` はビットを 3 つ左にずらすことで、`x * 8` と同じです。
- **右シフト `>>`**: `x >> 24` はビットを 24 個右にずらし、上の方のビットを下の方へ持ってきます。
- **XOR `^`**: ビットごとに「違えば 1」を計算します。`hash ^ (hash >> 24)` は「上の方のビットを下の方に混ぜ込む」操作です。
- **`~`**: 全ビットの反転です。符号なし整数では `~x` は `2^64 - 1 - x` と同じです。
- **ハッシュの「雪崩効果」**: 入力の 1 ビットを変えると、出力の約半分のビットが変わる性質のことです。よいハッシュ関数はこれを目指します。

## 何をしているか

7 行それぞれが、「掛け算」か「上位ビットを下位に混ぜる」かのどちらかです。

### 1. 掛け算の部分（1722、1724、1726、1728 行目）

- 1722 行目: `(~hash) + (hash << 21)`。コメントのとおり `(hash << 21) - hash - 1` と同じで、`hash * (2^21 - 1) - 1` にあたります。
- 1724 行目: `hash + (hash << 3) + (hash << 8)` は `hash * (1 + 8 + 256)` = `hash * 265` です。
- 1726 行目: `hash + (hash << 2) + (hash << 4)` は `hash * (1 + 4 + 16)` = `hash * 21` です。
- 1728 行目: `hash + (hash << 31)` は `hash * (2^31 + 1)` です。

掛け算は、下の方のビットの影響を上の方へ広げます。`hash * 265` なら、ビット 0 の変化がビット 0・3・8 に伝わり、繰り上がりでさらに上へ広がります。

### 2. XOR とシフトの部分（1723、1725、1727 行目）

掛け算は「下から上へ」しか影響を伝えません。そこで `hash ^ (hash >> 24)` のように、上の方のビットを右にずらして下の方に XOR で混ぜます。これで「上から下へ」の影響も生まれます。

### 3. 例で見る

`hash = 1` と `hash = 2` は 1 ビットしか違いませんが、最初の行で `1` は `2^21 - 2`、`2` は `2^22 - 3` になり、以後の段でさらに違いが広がっていきます。7 段を通るころには、どのビットが入力のどのビットに由来するのか、追いきれないほど混ざり合います。

## ここがすごい

**掛け算命令を使わない**: 定数との掛け算を、シフトと足し算の組み合わせに分解しています。掛け算命令が遅かった時代の CPU で特に有利な書き方です。今のコンパイラは逆に、このシフトと足し算を掛け算命令にまとめることもあります。コメントの `/* hash * 265 */` は、読む人のために意図を書き残したものです。

**逆算できる操作だけでできている**: 奇数を掛ける操作も、`x ^ (x >> k)` も、64 ビットの範囲で **元に戻せる**（逆関数がある）操作です。最初の行も、`~` と奇数倍・足し算の組み合わせなので元に戻せます。つまり、異なる入力は必ず異なる出力になり、64 ビットの値どうしでは衝突が起きません。ハッシュテーブルで使うときは出力の一部しか使わないので衝突は起きますが、「混ぜる段階で情報を失わない」のは整数ハッシュとして大事な性質です。

**交互に並べる設計**: 「下→上へ伝える操作（掛け算）」と「上→下へ伝える操作（右シフトの XOR）」を交互に並べることで、少ない段数ですべてのビットが互いに影響し合うようにしています。MurmurHash の仕上げ処理などにも見られる、整数ハッシュの典型的な構造です。

**使いどころ**: 暗号用のハッシュではないので、攻撃者が衝突を狙う場面には向きません。そういう用途には Valkey は鍵付きの SipHash を使います。この関数は、速さと「ほどよい散らばり」が欲しい内部用途向けです。

## まとめ

- 定数との掛け算は、シフトと足し算に分解できる（`x*265 = x + (x<<3) + (x<<8)`）。
- 掛け算は下位→上位、`x ^ (x >> k)` は上位→下位へビットの影響を伝える。
- 両方を交互に重ねると、少ない段数でよく混ざる。
- 元に戻せる操作だけで組むと、64 ビットどうしでは衝突しないハッシュになる。
