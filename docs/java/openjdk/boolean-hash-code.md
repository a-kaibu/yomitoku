## ひとことで

`Boolean.hashCode(value)` は、`true` なら `1231`、`false` なら `1237` を返します。

真偽値は 2 通りしかないので、`1` と `0` でもよさそうです。それなのに、なぜこんな半端な数なのでしょうか。どちらも **素数**（1 と自分以外で割り切れない数）で、ハッシュ値として扱いやすい性質を持っています。

## コード

```java:line-numbers=263
    public static int hashCode(boolean value) {
        return value ? 1231 : 1237;
    }
```

## 前提知識

- **`boolean`**: `true`（真）か `false`（偽）のどちらかの値をとる型です。
- **`hashCode`**: オブジェクトを表す整数を返すメソッドです。`HashMap` などが、データを入れる箱の位置を決めるのに使います。
- **`条件 ? A : B`**: 三項演算子です。条件が真なら `A`、偽なら `B` になります。
- **ハッシュ値の組み合わせ**: 複数のフィールドを持つオブジェクトのハッシュ値は、よく `31 * h + 各フィールドのハッシュ` のように、掛けて足しながら作ります（`Objects.hash` や `Arrays.hashCode` など）。
- **素数**: 2, 3, 5, 7, 11… のように、1 と自分自身でしか割り切れない数です。

## 何をしているか

### true と false で値を選ぶ

```java:line-numbers=264
        return value ? 1231 : 1237;
```

コードは三項演算子 1 つだけです。`value` が `true` なら `1231`、`false` なら `1237` を返します。

どちらの値も、Boolean クラスの仕様（Javadoc）に明記されているので、Java のどのバージョン・どの実装でも同じです。

## ここがすごい

### 0 と 1 を避ける理由

- **0 は「何もない」と区別しにくい**: 多くのハッシュの組み合わせ方では、0 を足しても値が変わりません。たとえば `31 * h + 0` は `31 * h` です。`false` のハッシュが 0 だと、「`false` のフィールドがある」ことと「そのフィールドがない」ことが同じハッシュ値になりやすくなります。
- **小さい値はほかの値と重なりやすい**: `0` と `1` は、`Integer` の `0` と `1`、空のコレクションなど、いろいろなもののハッシュ値とぶつかります。1231 や 1237 なら、ほかの代表的な値と偶然一致することが減ります。

### 素数である理由

ハッシュ表のサイズや、組み合わせのときに掛ける数（31 など）と **共通の約数を持たない** 数の方が、掛けたり余りを取ったりしたときに値が偏りにくくなります。偶数のハッシュ値は 2 のべき乗の大きさの表で下位ビットが偏る原因になりますが、素数（2 以外）は奇数なので、その心配も少なくなります。

1231 と 1237 は、差が 6 の近い素数のペアです。数そのものに特別な意味はなく、「ほどよい大きさの、異なる 2 つの素数」として選ばれたと考えられます。Java のコレクションフレームワークの設計で知られる Joshua Bloch 氏の著書『Effective Java』も、ハッシュ値の設計で 0 を避け、素数を使う考え方を紹介しています。

### とても小さな設計判断の価値

わずか 1 行ですが、「値が 2 通りしかないから適当でよい」と考えず、**組み合わされたときにどうなるか** まで考えて定数を選んでいます。小さな部品の質が、それを使う大きなデータ構造の性能を左右するのです。

## まとめ

- ハッシュ値に 0 や 1 のような小さい値を使うと、他の値とぶつかったり、組み合わせで消えたりしやすい。
- 素数のハッシュ値は、掛け算や余りの計算で偏りにくい。
- 部品の設計では、それが「どう組み合わされて使われるか」まで考える。
