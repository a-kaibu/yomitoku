## ひとことで

`LongMath.lessThanBranchFree(x, y)` は、`x < y` なら `1`、そうでなければ `0` を返す小さな関数です。`if` 文を使わず、**`x - y` の符号ビットを取り出す** だけでこの答えを作ります。

「分岐を使わない」ことには理由があります。CPU は `if` の条件を予測しながら先に処理を進めるので、予測が外れると遅くなります。値がランダムに変わるような場面では、この関数のような書き方の方が速く動くことがあります。

## コード

::: code-group

```java:line-numbers=108 [日本語訳]
  static int lessThanBranchFree(long x, long y) {
    // GWT（Java を JavaScript に変換する環境）で、ビット演算が意図どおり動くように二重の否定を書いている。
    // 通常の Java では二重の否定は最適化で消えるが、GWT では必要。
    return (int) (~~(x - y) >>> (Long.SIZE - 1));
  }
```

```java:line-numbers=108 [原文]
  static int lessThanBranchFree(long x, long y) {
    // The double negation is optimized away by normal Java, but is necessary for GWT
    // to make sure bit twiddling works as expected.
    return (int) (~~(x - y) >>> (Long.SIZE - 1));
  }
```

:::

## 前提知識

- **`long`**: 64 ビットの符号付き整数です。範囲は約 ±9.2×10^18 で、超えると回り込みます（オーバーフロー）。
- **符号ビット**: 最上位の 1 ビット（いちばん左）です。`1` なら負の数、`0` なら 0 以上の数を表します。
- **`~`（ビット反転）**: すべてのビットを `0` と `1` で入れ替えます。`~~x` は 2 回反転なので、元の `x` に戻ります。
- **`>>>`（符号なし右シフト）**: 右にずらし、左端には必ず `0` を入れます。`>>> 63` とすると、符号ビットだけが最下位に残ります。
- **`(int)` キャスト**: `long` を `int` に変換します。ここでは結果が `0` か `1` なので、下位 32 ビットに収まります。
- **`Long.SIZE`**: `long` のビット数で、64 です。`Long.SIZE - 1` は 63 になります。

## 何をしているか

### 1. 差を取る

```java:line-numbers=111
    return (int) (~~(x - y) >>> (Long.SIZE - 1));
```

`x = 3`、`y = 5` で追います。`x - y = -2` です。`-2` を 2 進数で表すと、符号ビットが `1` の数です。

### 2. 符号ビットを取り出す

`~~(x - y)` は `x - y` と同じ値なので、結果は変わりません。Java の JIT コンパイラが二重の否定を消すからです。

`>>> 63` で最上位の 1 ビットを最下位へ運ぶと、`-2` なら `1` が残り、`x < y` だったことがわかります。

### 3. 別の例で確かめる

`x = 5`、`y = 3` なら `x - y = 2` で、符号ビットは `0` です。結果は `0` で、`5 < 3` は偽なので正しいです。

`x = y` なら `x - y = 0` で、符号ビットは `0`。`x < y` は偽なので、これも正しく `0` になります。

## ここがすごい

- **分岐がない**: `return x < y ? 1 : 0;` と書けば同じ意味ですが、CPU にとっては分岐です。この関数は引き算とシフトだけなので、どんな値でも同じ速さで動きます。
- **オーバーフローを前提にする**: `x - y` は、差が `long` の範囲を超えるとあふれます。それでも正しく動くのは、呼び出し側で差が範囲内に収まることを確かめているからです。`IntMath.sqrt` のコメントでも、「この引き算は符号付きとして安全に扱える」と理由が書かれています。
- **GWT への配慮**: 二重の否定が消えない環境のための書き方として、コメントで理由が説明されています。最適化の結果が環境によって変わることを知っていて、コードに意図を残しているのです。
- **`@VisibleForTesting`**: この関数は内部用ですが、テストから直接呼べるように公開範囲を広げています。

## まとめ

- 2 つの数の大小は、差の符号ビットを取り出せば分岐なしで判定できる。
- 分岐をなくすと、値の予測しにくいデータでも速さが安定する。
- 引き算がオーバーフローしないことを確かめてから、この方法を使う。
