## ひとことで

`binary.BigEndian.Uint32(b)` は、バイト列 `b` の先頭 4 バイトを **ビッグエンディアン**（上位バイトが先）の 32 ビット整数として読みます。
`[]byte{0x12, 0x34, 0x56, 0x78}` なら `0x12345678` です。ネットワークのデータや多くのファイル形式を読むときに使われます。

注目は `_ = b[3]` です。値を捨てているだけの、一見無意味な 1 行ですが、これで関数が速くなります。

## 前提知識

- **エンディアン**: 複数バイトの数を並べる順番です。ビッグエンディアンは上位バイトから（`12 34 56 78`）、リトルエンディアンは下位バイトから（`78 56 34 12`）並べます。
- **境界チェック**: Go はスライスの範囲外にアクセスすると `panic` します。そのため、`b[i]` のたびに、コンパイラは「`i` は長さ未満か」を調べる命令を入れます。
- **`_ =`**: 値を捨てる書き方です。`_ = b[3]` は「`b[3]` を読むが、使わない」という意味です。
- **`(bigEndian)` というレシーバ**: `bigEndian` は中身のない構造体型で、名前のない受け取り手としてメソッドを定義しています。`binary.BigEndian` はこの型の値で、`binary.LittleEndian` と同じ使い方ができるようにするための工夫です。
- **`uint32(b[2])<<8`**: バイトを 32 ビット整数に変換してから左にずらします。変換しないと、8 ビットの範囲でずらして値が消えてしまいます。

## 何をしているか

### 1. 境界チェックをまとめる

```go:line-numbers=177
	_ = b[3] // コンパイラへの境界チェックのヒント。golang.org/issue/14808 を参照
```

`b[3]` を読みます。`b` の長さが 4 未満ならここで `panic` します。
ここを通過したということは「`b` の長さは 4 以上」です。コンパイラはこの事実を覚えているので、次の行の `b[0]`〜`b[3]` では **境界チェックを省きます**。

### 2. 4 バイトを組み立てる

```go:line-numbers=178
	return uint32(b[3]) | uint32(b[2])<<8 | uint32(b[1])<<16 | uint32(b[0])<<24
```

`b = [0x12, 0x34, 0x56, 0x78]` なら、

```
uint32(0x78)        = 0x00000078
uint32(0x56) << 8   = 0x00005600
uint32(0x34) << 16  = 0x00340000
uint32(0x12) << 24  = 0x12000000
OR を取ると           0x12345678
```

## ここがすごい

- **境界チェックの削減（BCE）**: この 1 行がないと、`b[3]`、`b[2]`、`b[1]`、`b[0]` の順にそれぞれチェックが入ることがあります（実際には一部まとめられますが、確実ではありません）。最初に最大の添字を確かめれば、残りは不要だとコンパイラが証明できます。issue 14808 で議論された最適化で、Go の高速なコードでよく使われるイディオムです。
- **コンパイラが 1 命令にする**: この「バイトを順に読んでシフトして OR する」形は、コンパイラが認識して、多くの CPU で **4 バイトを一度に読む命令 + バイト順の反転命令** に置き換えます。Go には「メモリをそのまま整数として読む」安全な方法がないので、安全な書き方で書き、コンパイラに最適化を任せています。
- **`unsafe` を使わない**: ポインタを無理やり変換すれば 1 回で読めますが、アライメント（メモリ上の位置の制約）や移植性の問題があります。この書き方ならどの CPU でも正しく動きます。

## まとめ

- `_ = b[n]` で先に最大の添字を確かめると、以降の境界チェックをコンパイラが省ける。
- バイトを順に読んで組み立てる素直な書き方は、コンパイラが専用命令にまとめてくれる。
- 安全な書き方を保ちつつ、コンパイラが最適化しやすい形に書くのが Go の流儀。
